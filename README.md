Part 1 Question 1:
Every request gets a new object, so data inside the class can be lost. That’s why we store shared data in a common place like a static HashMap. We also need to be careful because multiple users can change the data at the same time (race conditions).
Also, In jax-rs, a resource class is normally request scoped by default, which means that a new instance of the resource class is created for each incoming http request. This is useful because it prevents request-specific state from being accidentally shared between different clients. In other words, local variables and instance fields inside the resource class are generally safe for one request only, because they are not reused across multiple requests.
However, this does not mean that all application data is automatically shared or protected. In this coursework, the api must store its data using inmemory structures such as hashmaps and arrayList instead of a database. Because a fresh resource object may be created for each request, any data stored only in non-static instance fields inside the resource class could be lost when the request finishes. To avoid this, shared api data such as rooms, sensors, and readings should be stored in a common shared location, for example a separate service or repository class or static collection that remains available across requests. The coursework explicitly requires the use of data structures like hashmaps and arraylists for storage. 
This lifecycle decision also has an impact on thread safety. Even though each request gets its own resource instance, the shared collections holding the application data may still be accessed by multiple requests at the same time. For example, one client could be creating a room while another is deleting one, or one request could be adding a sensor while another is listing sensors. If ordinary unsynchronised collections are shared without care, this can lead to race conditions, inconsistent data, or overwritten updates.
To reduce this risk, the shared data structures should be managed carefully. One approach is to keep all shared data in a dedicated storage class and control modifications through well defined methods. Synchronisation can then be added where needed, or thread safe collections can be considered if appropriate. The key idea is that although the resource objects themselves are short lived, the underlying in memory data is shared across requests and therefore must be protected from concurrent modification.
Overall, the default request based lifecycle is helpful because it keeps each http request isolated, but it also means the developer must deliberately design a persistent shared in memory storage strategy and consider concurrency to prevent both data loss and race conditions. The coursework’s requirement to use in memory collections rather than a database makes this especially important.

The @consumes(mediatype.application_json) annotation defines the media type that the post method is able to accept. In this case, it tells jax-rs that the method only consumes request bodies sent in json format. when a client sends a request to create a new sensor, jax-rs checks the content type header of the http request before calling the method. If the content type is application/json, the framework accepts the request and attempts to convert the json body into a sensor object. this is important because the method logic relies on receiving structured json data that matches the fields of the sensor class, such as id, type, status, currentvalue and roomid.
If a client sends the data in a different format, such as text/plain or application/xml, the media type will not match what the method is configured to consume. in that situation, jax-rs will not treat the request as valid for that post method. instead of running the method, the framework will reject the request and normally return an http 415 unsupported media type response. this means the problem is not with the sensor data itself, but with the format in which the data was sent. as a result, the api is protected from attempting to process input that it is not designed to understand.
This behaviour improves the reliability and consistency of the api. by restricting the accepted format to json, the service makes its input requirements clear and ensures that request bodies can be deserialised correctly into java objects. it also reduces the risk of unexpected parsing errors, invalid conversions, or ambiguous client behaviour. therefore, the @consumes(mediatype.application_json) annotation is important because it enforces a clear contract between the client and the server about the format of data that must be used when creating a new sensor.

The filtering was implemented using @QueryParam("type"), which allows requests such as /api/v1/sensors?type=CO2. This is generally considered the better design because the sensor type is being used as a filter on the sensors collection, rather than identifying a completely different resource. The endpoint /api/v1/sensors represents the full collection of sensors, and the query parameter simply narrows that collection down to a subset that matches a condition. In other words, the resource remains the same, but the client is asking for a filtered view of it.
By contrast, an alternative design such as /api/v1/sensors/type/CO2 places the type inside the url path. This makes the filter look more like a fixed sub resource, as if CO2 sensors are a separate category of endpoint rather than a filtered result from the main sensors collection. Although this design can still work technically, it is less clear in terms of restful meaning. In rest, the path is usually used to identify resources and the structure of those resources, while query parameters are more appropriate for optional filtering, searching and sorting operations.
Using query parameters is also more flexible and scalable. The same endpoint can return all sensors when no filter is provided, or only matching sensors when a type is included. This makes the api simpler for clients to use because they do not need separate endpoints for each type of search. It also makes the design easier to extend in the future. For example, additional filters could be added in a natural way, such as /api/v1/sensors?type=CO2&status=ACTIVE or /api/v1/sensors?type=Temperature&roomId=LAB-101. This would be much harder to manage cleanly if every filter had to be placed inside the URL path.
Overall, the query parameter approach is superior because it clearly communicates that the client is filtering the sensors collection, keeps the endpoint structure cleaner, and provides greater flexibility for future expansion. It is therefore a more restful and maintainable design for searching and filtering collections.

Http 422 Unprocessable Entity is often considered more semantically accurate than http 404 Not Found in this scenario because the problem is not that the requested api endpoint itself is missing, but that the server cannot process part of the client’s otherwise valid request data. In this case, the client successfully sends a request to a real and existing endpoint such as post /api/v1/sensors, and the json payload is structurally correct. However, one field inside that payload, such as roomId, refers to a room that does not exist in the system. This means the request syntax is valid, the target resource path is valid, but the meaning of the submitted data cannot be accepted. That is exactly the kind of situation that 422 is designed to represent.
However, HTTP 404 Not Found is usually used when the resource identified by the request url cannot be found. For example, if a client requests get /api/v1/rooms/INVALID and that specific room does not exist, a 404 response is appropriate because the client is directly asking for a missing resource through the url. In the dependency-validation case, however, the client is not requesting a missing . Instead, the client is sending a valid request to create a new sensor, but one of the values inside the json body contains an invalid reference. Therefore, using 404 could be misleading, because it may suggest that the api route itself or the directly requested resource is missing, rather than indicating that the submitted data failed a business rule or integrity check.

Using 422 is also better from a rest design perspective because it gives the client a clearer explanation of what went wrong. It tells the client that the request was well formed and understandable, but the server could not apply it because the data breaks domain rules. In this coursework, the rule is that a sensor cannot be created unless its roomId points to a room that already exists. Returning 422 therefore communicates that the payload has semantic errors, not syntax errors. This helps client developers debug their applications more effectively, because they can immediately understand that they need to fix the roomId value rather than change the endpoint, request format, or http method.

For these reasons, http 422 is more precise and expressive than 404 for a missing linked reference inside a valid json payload. It reflects the fact that the server understood the request, the endpoint exists, and the json format is acceptable, but the request cannot be completed because the referenced dependent resource does not exist. This makes the api behaviour more accurate, predictable, and easier for clients to work with.

Exposing internal Java stack traces to external api consumers is dangerous from a cybersecurity perspective because a stack trace can reveal detailed technical information about how the server is built and where it failed. Instead of only telling the client that an unexpected server-side error occurred, a raw stack trace may disclose class names, package structures, framework components, method calls, file names, and sometimes even line numbers. This gives an attacker valuable insight into the internal architecture of the application and can make the system much easier to analyse and target. For this reason, returning a generic http 500 Internal Server Error response is much safer than exposing the full exception details to the outside world. 
One major risk is information leakage about the technology stack. A stack trace can show that the system is built using Java, jax-rs, Jersey, tomcat, and specific internal packages and resource classes. It may also reveal how requests are routed through filters, exception mappers, resource classes, and model objects. This helps an attacker identify the exact technologies and components in use, which can then be cross checked against known vulnerabilities, configuration weaknesses, or common attack techniques. In effect, the attacker gains a map of the application’s internal structure without having to reverse engineer it from scratch. 
Another serious risk is that stack traces may expose implementation details that help an attacker craft more precise malicious requests. For example, if a trace shows that a NullPointerException occurs in a particular method when a field is missing, the attacker learns how the server behaves when certain values are absent or malformed. If it shows an IndexOutOfBoundsException or a parsing failure, the attacker may infer assumptions made by the code about array sizes, request parameters, or input formats. This information can be used to probe for additional weaknesses, trigger denial-of-service style failures, or identify logic paths that were not safely validated. In other words, stack traces can help attackers move from guessing to targeted exploitation.
Stack traces can also reveal sensitive environment details. Depending on the exception, they may contain absolute file paths, server directory structures, configuration file names, deployed application names, internal host information, dependency versions, or library names. Even if no passwords or private data are directly shown, this kind of operational information is still highly useful to an attacker because it reduces uncertainty about the deployment environment. Knowing file paths or application structure may support later attacks against configuration files, log files, misconfigured endpoints, or known framework specific weaknesses.
For these reasons, exposing raw Java stack traces is risky because it can reveal framework details, package names, class structures, method names, line numbers, file paths, configuration hints, and behavioural weaknesses in the code. All of this can help an attacker understand the system more deeply and plan more effective attacks. A generic 500 response combined with internal server-side logging is therefore the safer and more professional approach.

Using jax-rs filters for logging is advantageous because logging is a cross-cutting concern, meaning it applies to many parts of the api rather than to one specific business operation. In this coursework, every request and every response should be observable, regardless of whether the client is accessing rooms, sensors, or sensor readings. If logging were written manually inside each individual resource method using Logger.info(), the same code would need to be repeated again and again across many endpoints. This creates duplication, increases the chance of mistakes, and makes the code harder to maintain. A filter solves this by allowing the logging behaviour to be written once and automatically applied to all matching requests and responses.

Another important advantage is separation of concerns. Resource classes should mainly focus on application logic, such as creating a room, validating a sensor, or adding a reading. Logging is not part of that core business logic; it is part of monitoring and observability. By placing logging inside jax-rs filters, the resource methods stay cleaner, shorter, and easier to read because they are not cluttered with repetitive technical statements. This improves the overall design of the api and makes it easier for developers to understand what each method is actually supposed to do.

Filters also provide much better consistency. When logging is implemented manually, different methods may log slightly different information, use different message formats, or accidentally omit important details. One method might log the url, another might only log the http method, and another might forget to log the status code entirely. A jax-rs filter guarantees that all incoming requests are logged in the same structured way and that all outgoing responses are recorded with the same level of detail. This is especially useful for debugging, auditing, and tracing user activity through the api.

In addition, filters are more scalable. As the api grows and more resource classes are added, the logging behaviour does not need to be rewritten for every new endpoint. The same filter continues to work across the whole application. If the developer later decides to change the logging format, include timestamps, or capture extra metadata, that change can be made once in the filter instead of being edited in many different files. This saves development time and reduces the risk of inconsistent updates.

For these reasons, jax-rs filters are a more professional solution for cross cutting concerns like logging. They reduce duplicated code, keep resource methods focused on business logic, ensure consistent logging across the api, and make the application easier to maintain and extend. This is much more effective than manually inserting Logger.info() statements inside every individual resource method.
